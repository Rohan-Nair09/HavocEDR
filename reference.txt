ABSTRACT
Retail traders, Python strategy authors and small trading teams usually depend on a fragmented set 
of tools – separate charting websites, notebooks for backtesting, exchange web terminals for order 
entry and bots for alerts. Many of these tools are hosted by third parties, which forces users to hand 
over their exchange API keys and proprietary strategy code, and none of them gives AI assistants a 
safe, controlled way to take part in the trading workflow.
QuantTrade is an open-source, self-hosted AI Trading Operating System that turns trading ideas 
into Python strategies and carries them through backtesting, paper (signal) trading, live execution  
and monitoring inside a single Docker-based stack owned by the user. The backend is built with  
Python 3.12, Flask and Gunicorn, uses PostgreSQL 18 for durable state, Redis 8 for caching and job 
queues, Celery for background jobs and Apache Kafka for strategy events. A Vue.js web client and 
a mobile H5 client provide AI market research, an indicator IDE, a Strategy API V2 editor, a  
Backtest Center, strategy deployment, Quick Trade and portfolio monitoring.
Live orders are routed through native adapters for six crypto exchanges (Binance, OKX, Bitget,  
Bybit, Gate, HTX) and two brokers (Interactive Brokers and Alpaca). Exchange keys are encrypted 
at  rest,  users  are  protected  by  bcrypt  passwords,  JWT  sessions  and  TOTP  multi-factor  
authentication, and every live entry can pass through an AI decision filter. AI agents connect  
through a scoped Agent Gateway and a Model Context Protocol (MCP) server that is paper-only by 
default. The backend test suite of 3,346 automated unit tests passed successfully, and the complete 
system is deployed with Docker Compose.

CHAPTER – 1
INTRODUCTION
1.1 Purpose
- The  purpose  of  the  project  entitled  “ QuantTrade  –  AI  Trading  
Operating System” is to build a self-hosted, AI-augmented quantitative  
trading  platform  that  unifies  market  research,  strategy  development,  
backtesting, paper trading, live execution and monitoring in one system  
that runs on the user’s own hardware.
- Today  traders  and  quantitative  researchers  stitch  together  many  
disconnected  tools  and  expose  sensitive  exchange  credentials  and  
proprietary strategy code to third-party cloud services. QuantTrade keeps  
algorithms and credentials under the operator’s control.
- The project also provides a safe, standardised way for AI agents (Cursor,  
Claude Code, Codex and others) to participate in the trading workflow  
through the Model Context Protocol (MCP), with paper-only defaults and 
strict risk guardrails.
1.2 Scope
- Multi-market data: Crypto, US stocks, HK stocks, CN A-shares, Forex,  
Futures and MOEX with canonical symbol identifiers.
- AI market research with multiple LLM providers, exportable PDF reports 
and an AI chat copilot.
- Python indicator IDE and Strategy API V2 editor with AI generation,  
validation and version history.
- Server-side Backtest Center with performance and benchmark metrics,  
and strategy evolution (parameter optimisation).
- Signal (paper) and live deployment across Binance, OKX, Bitget, Bybit,  
Gate, HTX, Interactive Brokers and Alpaca.
- Quick Trade with an AI pre-trade decision filter, portfolio monitoring,  
price alerts and multi-channel notifications.
- Agent Gateway and MCP server for AI agents; authentication with MFA  
and role-based access control.
- Out of scope: high-frequency co-located trading, custody of user funds and 
investment advice.
13

1.3 Technology and Tools
Front End technology used in the application :
▪ Vue.js :-
- Vue.js is a progressive JavaScript framework for building single-page  
applications (SPA).
- QuantTrade’s  web  client  is  a  Vue.js  SPA  with  a  component-based  
structure and left-side navigation between modules.
- Ant Design Vue provides ready-made UI components such as tables,  
forms, dialogs and metric cards.
▪ KLineCharts & ECharts :-
- KLineCharts renders real-time candlestick (K-line) charts with indicator  
overlays and trade markers.
- ECharts  renders  equity  curves,  drawdown  charts,  heat-maps  and  
dashboard visualisations.
▪ Nginx & Capacitor :-
- Nginx serves the built web (port 8888) and mobile H5 (port 8889) clients  
and proxies API calls to the backend.
- Capacitor packages the mobile H5 client as a native mobile application.
Back End technology used in the application :
▪ Python 3.12, Flask & Gunicorn :-
- Python is the main backend language because of its rich data-science and  
trading ecosystem (pandas, NumPy, TA-Lib).
- Flask 3.1 with flask-smorest implements the REST API and generates  
OpenAPI documentation.
- Gunicorn  serves  the  Flask  application  in  production  using  threaded  
(gthread) workers.
▪ PostgreSQL 18 & Redis 8 :-
- PostgreSQL  stores  all  durable  data:  users,  strategies,  orders,  trades,  
backtests and audit logs (100+ tables).
- Redis  is  used  as  a  disposable  cache  (allkeys-lru)  and,  as  a  separate  
instance, as the durable Celery job broker (AOF, noeviction).
▪ Celery & Apache Kafka :-
- Celery runs finite background jobs such as backtests, AI analysis and  
reports.
- Kafka is the event backbone that distributes closed-bar events to sharded  
strategy evaluator workers.
14

▪ Docker & Docker Compose :-
- All services run as containers orchestrated by Docker Compose v2, giving 
the same environment on Linux, macOS and Windows (WSL2).
▪ AI integration :-
- LLM providers: OpenRouter, OpenAI-compatible APIs, Google Gemini,  
DeepSeek, Grok, MiniMax and LiteLLM.
- Model Context Protocol (MCP) server for AI agents; TypeSafe JEV for  
typed pre-trade decisions.
1.4 Problem Statement
Traders  and  quantitative  researchers  today  are  forced  to  stitch  together  
multiple disconnected tools for market research, strategy backtesting, paper trading  
and live order execution. Many of these tools depend on external cloud platforms,  
exposing  sensitive  exchange  credentials  and  proprietary  strategy  code  to  third  
parties, and they offer no standardised way for AI agents to safely participate in the  
trading workflow.
Most existing platforms also lack strict execution guardrails, so it is easy to  
accidentally deploy an untested strategy with real capital, or to send duplicate orders 
when a network request is retried. Positions spread across several exchanges and  
brokers must be tracked manually, and there is no single place to see the complete  
portfolio.
Therefore,  there  is  a  need  to  develop  a  self-hosted  quantitative  trading  
platform capable of:
- Ingesting and processing multi-asset market data locally.
- Writing strategies once and running the same code in backtest, paper and  
live modes.
- Simulating realistic paper trading before capital is risked.
- Routing live orders securely and exactly once across multiple exchanges  
and brokers.
- Allowing AI agents to safely generate, test and adjust strategies through  
MCP.
1.5 Objectives
The objectives of QuantTrade are:
1. Ingest  and  normalise  multi-asset  market  data  with  canonical  symbol  
identifiers.
15

2. Support  AI-driven  market  research  and  strategy  generation  through  
multiple LLM providers and MCP.
3. Provide  a  Strategy  API  V2  programming  model  whose  code  runs  
unchanged in backtest and live runtime.
4. Provide a Backtest Center with realistic fees and slippage and robust  
parameter evolution.
5. Simulate fills, positions and PnL in signal-only virtual accounts before  
going live.
6. Route market and limit orders to six crypto exchanges and two brokers  
with idempotent, durable order handling.
7. Keep paper trading as the default, with explicit confirmation and AI/risk  
checks before live entries.
8. Aggregate positions, alerts and notifications across venues in one portfolio 
view.
9. Protect users with encrypted credentials, hashed passwords, MFA and  
role-based access control.
10. Maintain audit logs for every AI-agent interaction and pre-trade decision.
11. Provide  a  responsive,  dark-mode  web  dashboard  and  mobile  client,  
deployable with a single command.

3.2 Constraints
3.2.1 Hardware Limitation :
- The full stack runs about fifteen containers; hosts with less than 8 GB  
RAM may need to run without the optional monitoring overlay.
- Insufficient disk space can stop PostgreSQL or the job Redis and halt  
trading workers.
- For Interactive Brokers, the TWS / IB Gateway must run on a machine  
reachable by the server.
3.2.2 Reliability Requirements :
Since many strategies and users can be active at the same time, the system  
must never lose or duplicate an order. Commands and orders are stored durably in  
PostgreSQL with idempotency keys, strategy ownership is protected by leases and  
heartbeats, and failed jobs are retried a bounded number of times. Workers publish  
heartbeats and alerts are raised within two minutes if a required worker is missing.
Reliability  also  depends  on  validation.  All  API  inputs  are  validated  by  
schemas; if a request violates a validation rule the user receives a clear error message 
and the record is not saved until it is corrected.
3.2.3 Safety and Security Consideration :
- Exchange credentials and MFA secrets are encrypted with Fernet using a  
dedicated CREDENTIAL_ENCRYPTION_KEY.
- Passwords are hashed with bcrypt; sessions use HS256 JWTs with token  
versioning.
24

- Production containers run as a non-root user with a read-only filesystem;  
databases are never exposed publicly.
- AI agents are paper-only unless three independent switches allow live  
trading.

A session is maintained with a JWT that is sent in the Authorization: Bearer

def login_required(f):
    @wraps(f)
    def decorated(*args, **kwargs):
        auth = request.headers.get("Authorization", "")
        token = auth[7:] if auth.lower().startswith("bearer ") else None
        if not token:
            return jsonify({"code": 401, "msg": "Token missing", "data": None}), 401
        payload = verify_token(token)        # signature, expiry, token_version
        if not payload:
            return jsonify({"code": 401, "msg": "Token invalid or expired"}), 401
        g.user_id = payload["user_id"]
        g.user_role = payload["_verified_user_role"]   # role from database
        return f(*args, **kwargs)
    return decorated

6.3 Coding Standards
A well-defined coding standard keeps the code readable and maintainable.  
QuantTrade follows these rules:
- Python code follows PEP 8 and is checked by the Ruff linter in CI ( ruff 
check app scripts tests).
- HTTP routes stay thin – they validate input and delegate to services; long-
running loops belong to workers.
- Every SQL statement uses parameters, never string concatenation.
- Monetary values use DECIMAL types; timestamps are stored in UTC.
53

- Every API change updates the OpenAPI specification and passes the  
compatibility workflow.
- Snake_case  for  functions  and  variables,  PascalCase  for  classes,  
UPPER_CASE for constants and environment variables.
6.3.1 Comment Standards :
Comments describe what is happening, why it is done, what parameters mean 
and any side effects. The standards followed are:
- Every  module,  class  and  public  function  starts  with  a  docstring  
("""...""").
- Inline comments use # and are indented at the same level as the code they 
describe.
- Comments explain why a decision was taken (for example, why an exit  
bypasses the AI filter), not just what the code does.

CHAPTER – 8
LIMITATIONS AND FUTURE ENHANCEMENT
8.1 Limitations
Though we tried our best in developing this system, it has some limitations:
- Strategy API V2 backtests do not yet model crypto funding payments.
- The full stack needs about 8 GB RAM, which is heavy for small machines.
- The AI decision filter does not yet cover grid, DCA and martingale  
strategies.
- Interactive Brokers requires TWS / IB Gateway running on the user’s  
machine.
- Backtest  results  depend  on  the  quality  of  historical  data  from  free  
providers.
- AI output can contain errors and must be reviewed by a human.
- HK/CN stocks, Forex and Futures are supported for data and backtesting  
only, not live trading.
- The web and mobile client source code are published separately under  
their own licence.
8.2 Future Enhancement
There is always scope for enhancement. The following changes can increase  
the capability and efficiency of the system:
- Funding-fee  modelling  and  more  realistic  order-book  simulation  in  
backtests.
- Additional exchanges, brokers and asset classes such as options.
- Multi-host scaling of strategy evaluators (hyperscale architecture).
- Native mobile notifications and richer mobile trading features.
- More  AI  skills,  such  as  automatic  strategy  review  and  explainable  
decisions.
- Portfolio-level risk management across strategies.
- Support for options strategies and Greeks-based risk.
- A visual (no-code) strategy builder for non-programmers.
- Paper-trading competitions and a community leaderboard.

CHAPTER – 9
CONCLUSION
QuantTrade  successfully  brings  AI  research,  strategy  development,  
backtesting, paper trading, live execution and monitoring together in a single self-
hosted platform. The layered, process-separated architecture keeps the web API  
responsive while dedicated workers handle trading, scheduling and background jobs. 
Durable commands, idempotency keys, leases and transactions prevent duplicate or  
lost orders, and encrypted credentials, MFA, role-based access control and paper-
only AI agents protect users’ capital and data.
The project was developed by following the complete software development  
life cycle through the fifteen laboratory experiments: requirement analysis and SRS, 
design, environment setup, frontend and backend implementation, API integration,  
security, CRUD operations, testing, optimisation, documentation and deployment.  
The automated test suite passed successfully and the system was deployed with  
Docker Compose. QuantTrade therefore fulfils its objective of giving traders an  
institutional-style, AI-augmented trading platform that remains fully under their own 
control.
